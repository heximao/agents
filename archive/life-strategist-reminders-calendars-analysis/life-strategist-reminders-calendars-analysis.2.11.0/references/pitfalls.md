# 常见陷阱

真实分析执行中发现的 21 条陷阱。**运行分析之前先加载本文件。**

- **`priority` 字段可能是 int 也可能是 string —— 直接用 `>=` 比较会在解析中途崩溃。** 一律用 `int(x.get('priority', 0))` 包在 try/except 里强制转换。一个 70 行解析脚本在第 52 行崩溃，整个输出就没了。
- **快照字段名必须与源数据完全一致——查错名字只会静默返回 None（不报 KeyError）。** 日历字段是驼峰命名：用 `startDate`、`startDateLocal`、`endDateLocal`、`allDay`、`hasRecurrences`、`recurrenceRule`，绝不用 `start_date`。提醒事项的列表名字段是 `list`——用 `listName` 过滤项目列表会匹配到零条。完整字段表见 `scripts/scan-calendars/README.md`。
- **偏离 30 分钟网格的事件时长是异常，且时长合计是量化过的。** 日历规则：30 分钟粒度、最小 30 分钟、超出按 30 分钟步进（时长 = ceil(需求/30)×30）。45 分钟的事件违反网格——标记出来。又因为短任务会被抬到 30 分钟下限，日历合计会高估短任务的实际投入；用时长做分配/节奏分析，不要做秒表精度的记账。
- **把重叠事件时长直接相加会高估实际墙钟时间。** 并发事件（原则 3）意味着同一墙钟分钟可能被记录在两个或多个事件下。做时间账合计时按墙钟时间去重（区间并集），不要累加原始时长——否则 1 小时实际时间配两个重叠事件会读成 2 小时。
- **快照里的 `completionDate` 是 UTC；`completionDateLocal` 是北京时间。** `01:23` UTC = `09:23` 北京。所有日期比较都用 `completionDateLocal`；绝不要不转换就直接截取 `completionDate`——日期边界会偏 8 小时。
- **重复提醒事项的 `dueDate` 是过时的**——一条未完成的每日习惯保留它原始/过去的 dueDate，而不是下一次发生时间。不要对习惯用 dueDate 推算「今天到期」；按 `recurrenceRule.frequency == 'daily'` 分类，把所有未完成的每日习惯都视为「今天到期」。对非习惯条目，`dueDateLocal[:10] == today` 判断是安全的，因为一次性/每周/每月条目携带真实截止日期。
- **已完成的每日习惯实例会丢失 `recurrenceRule`（Apple 在完成时剥离它）。** 采集层的 `isHabit = (recurrenceRule.frequency == 'daily')` 会把已完成实例判为 `false`。做习惯一致性分析时，先从「未完成的每日习惯」构建活跃习惯标题集合，再用标题把已完成条目匹配回该集合——这是分析层技巧（采集层忠实记录了剥离事实，不要到采集脚本里「修」它）。
- **快照的 `lists` 计数层会省略空分组的键**——0 条目的列表根本不出现在 `lists` 字典里。键缺失 ≠ 计数为 0；陈述证据基础时要写「键缺失（对比上一份快照）」，不能写「降到 0」。
- **快照反映的是扫描时刻的状态，不是实时状态。** 09:21 的快照显示今日完成 0 条，不代表没人做——只代表 09:21 时记录为完成的是 0 条。13:00 的快照会捕获 09:21 到 13:00 之间完成的条目。按归档原样分析；不要用实时 `remindctl` 调用补充——归档是权威来源，4 时点 cron 保证数据延迟不超过约 5 小时。
- **收集箱里的元规则不是黑洞。** 标题为【Agent请跳过】的条目是用户手工制定的任务分类规则（①立即做→闹钟 ②固定时间→日历 ③<15min→提醒）。它们被有意保持未完成、无截止日期。绝不标记删除；在黑洞扫描中跳过它们。
- **13:00 饭后触发器已退役（2026-10-21），午后启动由 cron job 54cff38091c1 驱动。** 原 Apple Reminder 13:00 每日重复项已被「每日-提醒事项-日历-跟踪」cron 替代——该 cron 在 8/13/17/22 时点 10 分运行，加载 life-strategist-reminders-calendars-analysis skill 分析快照并推送微信消息，内容覆盖原触发器催行动功能 + 上午时间诊断 + 日历时间块 + 下一步动作。不再需要在 Reminders 快照中检查 13:00 触发器项；分析运行本身即证明午后启动机制在工作。
- **日历上的系统任务是回避模式的证据，不是无辜的排程。** 当你在黄金工作时段看到「更新性格」「Cron功能开发」「profile.yaml」「SOUL更新」「gitignore」，套用工具过度投资闸门：这能在 2 周内产生收入吗？不能 → 标记为系统任务入侵。用户的核心回避机制是用系统搭建替代收入行动，日历是这件事客观显形的地方。
- **不要把系统清理当作优先行动项推荐。** 「清理你的提醒事项列表」或「重整你的日历」本身就是系统管理任务，会触发同一个回避循环。如果分析发现需要清理，把它们打包进「系统清理（不占工作时段）」小节，明确标注为周末/晚间工作，绝不作最高优先级。
- **已完成的提醒事项没有对应日历事件，是数据完整性缺口，不只是记录缺失。** 按原则 2，过去的日历事件是用户的实际时间日志。一条已完成的非习惯任务没有对应的过去事件，意味着要么事件没建（需补建），要么完成标记是错的（需纠错）。反向检查（透镜 7）能抓到它——但标题匹配是模糊的：用关键词重叠（例如提醒事项标题和日历事件标题里都有「简历」），不要精确匹配，因为用户可能在这两个系统里用不同措辞。
- **进行中事件的 endDate ≠ 整个活动链的完成时间。** 13:15 分析时「做午餐」（12:30-13:30）正在进行，endDate=13:30 是「做完午饭」，分析却表述为「13:30 吃完」——实际后续紧接「吃午餐」（13:30-14:00），14:00 才吃完。双错：①只取当前事件 endDate 作为「完成时间」，未追踪后续同主题事件链（做→吃是连续活动）②自然语言混淆「做完」与「吃完」。规则：分析「用户何时完成 X 活动」时，沿后续同主题事件链追踪到末事件 endDate 作为真正完成时间；表述严格区分 startDate=「开始」、endDate=「结束」，不得将 startDate 或前序事件 endDate 说成整个活动链的「完成」时间。
- **处理日历 JSON 时必须始终区分过去/未来事件语义（原则 2）。** 过去的时间块 = 用户实际做了什么（行为日志），不代表任务完成——「16:00-17:00 做了 social 简历」≠「social 简历写完了」，是否完成要看 Reminders isCompleted。未来的时间块 = 用户计划做什么（计划分配），不代表确定事实——用户随时会改 title/时间/删除。规则：①过去时间块用「花了 X 时间做 Y」而非「完成了 Y」②未来时间块用「计划 X 做 Y」而非「已排好 Y」③任务完成状态以 Reminders isCompleted 为准，不以日历时间块存在为准④用户反馈「已完成/已删除/已改时间」时，以用户反馈为准。⑤日历有过去时间块 + Reminders 未勾选 = 状态不一致 → 报告结论问用户「做完了没？」→ 完成了→提醒去 Reminders 勾选完成 / 没完成→提醒修改 Reminders 截止时间。不得同时放在「今日完成」和「今日到期未完成」两个矛盾位置。
- **引用用户反馈/历史事件时禁止发明时间周期。** 报告中引用用户说过的话，时间表述只允许两种：①实际记录日期（「你 10-23 说过…」）②无时间指向（「你自己说过…」）。除非该周期可在快照数据（dueDateLocal / completionDateLocal / 文件名日期 / 示例日期标注）中验证，否则不得使用「上周 / 前几天 / 之前 / 那天」等相对周期。技能 Self-Update 示例是历史反馈的主要文本来源，旧示例可能不带日期——无日期 = 日期未知，引用时不赋予任何时间。实测案例（2026-10-23）：17:10 报告把当天 12:09 的用户反馈写成「你上周自己说过『为了写简历而写简历让我抗拒』」——反馈实际只有 5 小时历史，「上周」纯属臆造，用户当场识破（「时间周期错位」）。教练引用错误的时间记忆比不引用更伤信任：它让整个分析系统的时序可靠性存疑。
- **标题匹配前必须剥离 emoji，且不得对四类循环做算术。** 用户规则记录「AI 目前无法识别表情」——同一任务在提醒事项和日历里可能一处带 emoji、一处不带，而透镜 7 的双向检查靠标题关键词重叠。不先剥离 emoji 会产生两类误报：正向误报「任务没有时间块」，反向误报「完成但无记录」。同源的三条边界同样必须遵守：①智能列表与文件夹的分组语义已丢失，不得声称「某文件夹下有几条」②小时循环、工作日循环、周末循环、周期内特定日期循环无法识别，不得据此推算下次到期时间或判定逾期③循环只可靠识别 daily / weekly / monthly / yearly 四种。详见 `user-maintenance-rules.md` 第四节。
- **同一 ID 跨快照是同一事件的「不同版本」，不是两条事件；而同一标题可能对应多个 ID。** 两个系统用的是**相反**的身份规则：日历按 `id` 对齐（标题会被整体换掉，实测 21/123 个事件改过标题，`ID 1908` 从「Cron 增加功能」改成「做午餐」），提醒事项按 `title` 聚合（每日习惯完成即生成新 ID，实测 49 个标题对应多个 ID）。用错规则会同时产生漏算与重复计算——把 23 份快照里出现 23 次的事件算成 23 件事，或把改名后的同一条记录当成新任务。三条强制推论：①统计事件数/总时长前按身份去重，只取最新版本②「某天做了什么」按最终 `startDateLocal` 归属，不按快照日期归属（同一 ID 会跨天漂移，实测 `ID 2169` 从 10-25 15:30 漂到 10-26 16:00）③窗口（`daysBack 7 / daysAhead 30`）外消失不是删除，判定删除需「最终 `startDateLocal` 仍在后一份快照 window 内」且「该 ID 未出现」，实测窗口内删除为 0。详见 `change-semantics.md`。
- **不要给单份快照里的过去时间块加不确定性对冲。** 「跨快照记录会被编辑」不等于「单份快照不可信」，这是两个层次。今天快照里看到昨天 13:00-16:30「修改简历，定稿汇联工作经历」（`id 2165`，`lastModified` 10-25 16:00 落在区间内，说明是活动进行中/刚结束时按实际用时修正的日志证据），正确表述是「昨天 13:00-16:30 你在定稿汇联工作经历」；写成「可能在做…但记录可能被改过」既没有信息量，又让整份分析显得不可信。留白只留给「做完没有」——判定看提醒事项 `isCompleted`，日历块只回答「当时在做什么」。跨快照可变性只在做跨期对比时才提，且必须注明基于哪一份快照（`scan_time_local`）。
- **同一个 ID 装完全不同的事，是使用习惯，不是数据错误。** 用户会在原有时段上直接改写标题，把一条日程换成另一件事。实测 21 个改过标题的事件中约 10–12 个属此类（字符集 Jaccard <0.3），占全部 123 个事件约 9%——**每次分析都会遇到，是常态不是偶发**；`ID 2034` 一个 ID 装过 4 件事（口头演练 → 自我介绍 → 定稿汇联 → 定稿自我评价）。看到「同 ID 标题剧变」时：❌ 不得报为数据异常 / 采集错误 / 记录损坏 / 建议修复；❌ 不得建议用户改为删除重建（那会把历史从一份快照挪进快照序列，读取档位从 L0 推到 L2）；✅ 按「该时段被重排 N 次」读，它是计划不稳定的直接证据。两条派生约束：①这类记录的标题只反映最后一版，**不得用于透镜 7 的标题匹配**（会漏配更早版本对应的提醒事项，产生「没有时间块」的假报）②不得用其历史版本做「同一任务」的纵向追踪。判定口径见 `change-semantics.md` 第二节。
