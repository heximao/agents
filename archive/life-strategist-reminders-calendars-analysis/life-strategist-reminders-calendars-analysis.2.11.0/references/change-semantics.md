# 数据变化语义（快照是同一份数据的连续版本）

> **一句话**：快照不是独立的抽样，是同一份数据的**连续版本**。分析的对象不是「一批事件」，是「一批被反复编辑的记录」。本文件说明这些记录怎么变，以及因此哪些分析动作是合法的、哪些是错的。

## 零、前提

用户维护日历和提醒事项的方式是**手动编辑，不删除**。这意味着：

- 一条记录的生命周期是「创建 → 被改 N 次 → 一直存在」，而不是「创建 → 结束 → 消失」。
- 跨快照的差异，绝大多数是**同一件事的不同版本**，不是不同的事。
- 「消失」在数据里几乎不存在；看到消失，先怀疑窗口滚动（见第二节），不要怀疑删除。

## 一、身份：ID 是唯一身份，标题不是

| 用作身份 | 是否可靠 | 原因 |
|---|---|---|
| `id` | ✅ **唯一可靠** | 跨快照稳定，创建后不变 |
| `title` | ❌ 不可靠 | 会被改写，甚至整条换掉（实测 21/123 个日历事件标题变过） |
| `creationDate` | ✅ 辅助 | 不变，可用于判断「这条记录有多老」 |
| `lastModifiedDateLocal` | ✅ 变更标记 | **唯一能判断「这条被改过」的字段** |

**标题可以完全换掉**，不只是微调。实测样例（同一 ID）：

- `ID 1908`：`Cron"每日-提醒事项-跟踪"增加功能并通过 Agent…` → `做午餐`
- `ID 1977`：`吃早餐` → `吃午餐`

所以：**跨快照对齐必须用 ID**。按标题找历史，会同时漏掉改名后的记录、又把不同记录误认成同一条。

## 二、日历的变更模型

### 只编辑，不删除

实测 2026-10 全月 23 份快照：**窗口内消失的事件数 = 0**。没有删除，只有编辑。

### 可变的字段

| 字段 | 会不会变 | 说明 |
|---|---|---|
| `startDateLocal` / `endDateLocal` | **频繁变** | 57/123 个事件至少改过一次；最多的一条改出 **9 个版本** |
| `title` | 会变 | 21/123 个事件改过，可整体换掉 |
| `calendar` | 会变 | 换日历归属 |
| `id` / `creationDate` | **不变** | 身份锚点 |
| `lastModifiedDateLocal` | 每次编辑刷新 | 变更标记 |

### 标题变更的两种类型（必须区分）

实测 21 个改过标题的事件，约一半是「同一件事换措辞」，另一半是「同一个 ID 被用来装另一件事」。两者分析含义完全不同：

| 类型 | 特征 | 实测样例 | 分析处理 |
|---|---|---|---|
| **改名** | 关键词高度重叠，主题不变 | `ID 1917` 简历完善：补Clash-Proxy段3条STAR要点 → 修改简历，Clash-Proxy 项目补3条STAR要点 | 同一件事，ID 可正常纵向追溯 |
| **槽位复用** | 关键词几乎不重叠，换成另一活动 | `ID 1908` Cron 增加功能 → 做午餐；`ID 1977` 吃早餐 → 吃午餐 | **不是一件事**。不得用该 ID 的历史版本做同一任务的纵向追踪；时间账按最终标题计 |

判定口径：标题关键词集合重叠 **≥50% 视为改名**；**<30% 视为槽位复用**；介于两者之间标记待确认，不要硬判。

**槽位复用是用户的固定习惯，不是数据故障。** 按字符集 Jaccard 粗筛，21 个改过标题的 ID 中 **12 个低于 0.3**（其中 1–2 个是度量误判，实际约 10–12 个），占全部 123 个事件的约 9%。**这是常态，不是偶发**——分析时每次都会遇到。

看到「同一 ID 标题剧变」时：

- ❌ 不得报为数据异常 / 采集错误 / 记录损坏 / 建议修复
- ❌ 不得建议用户「以后改成删除重建」——那会把历史从一份快照挪进快照序列，分析成本反而上升（见第八节读取档位）
- ✅ 按「该时段被重排 N 次」读，它是计划不稳定的直接证据

两条派生约束：

1. **这类记录不能用于透镜 7 的标题匹配**——它的标题只反映最后一版，拿它去匹配提醒事项会漏掉更早版本对应的任务，产生「没有时间块」的假报。
2. **不得用它的历史版本做「同一任务」的纵向追踪**——那是 N 件事，不是一件事的 N 个阶段。

**槽位复用是信息，不是噪声。** 一个 ID 被反复换成不同活动，说明**这个时段被反复推翻**——这是计划不稳定的直接证据。极端案例 `ID 2034` 先后装过 4 件事：

```
口头演练：把项目经历讲成3分钟版本 → 口头演练：自我介绍
→ 修改简历，定稿汇联工作经历 → 修改简历，定稿自我评价
```

正确读法是「这个块被重排了 3 次」，不是「一件任务的四个阶段」。

### 跨天漂移（最容易被误读的一种）

同一个 ID 会从一天漂到另一天。实测 `ID 2169`（修改简历，定稿杰拓工作经历）：

```
created 10-24 22:52 → 排 10-25 15:30-17:00
modified 10-25 16:00 → 10-25 16:30-18:00
modified 10-25 21:57 → 10-26 13:30-15:00   ← 跨天
modified 10-26 10:33 → 10-26 15:00-16:00
modified 10-26 16:00 → 10-26 16:00-17:00
```

推论：**「某天发生了什么」不能靠「那天的快照里有哪些事件」回答**。必须按每条记录**最终版本的 `startDateLocal`** 归属到日期。否则同一件事会在两天里各算一次，或者凭空从某天消失。

### 窗口滚动：消失 ≠ 删除

日历快照带 `window` 字段：

```json
{"daysBack": 7, "daysAhead": 30, "startLocal": "2026-10-19", "endLocal": "2026-11-25"}
```

事件滑出 `[startLocal, endLocal]` 就从快照里消失，**这是窗口过期，不是删除**。判断删除的唯一方式：**该事件最终的 `startDateLocal` 仍落在后一份快照的 window 内，却没有出现**。

副作用：做 7 天以上的趋势或对比时，**早期快照是唯一数据源**——晚期快照已经看不到它们了。

## 三、提醒事项的变更模型

### 只增不删（append-only）

实测 27 份快照：**没有任何 ID 消失**。条目数从 192 单调增长到 381，全部来自新增。

推论：**总条目数不是健康指标**。它只反映「累积了多少」，不反映「积压了多少」。要看完成率、新增率、逾期存量。

### 每日习惯：完成即生新实例

- 一条每日习惯完成时，Apple 立刻生成一个**新 ID** 的未完成实例。
- 所以**同一个标题会对应多个 ID**（实测 49 个标题如此，最多的 `每天 泡茶…` 有 12 个 ID）。
- 已完成的历史实例保留在原 ID 上，`recurrenceRule` 被剥离（见陷阱 7）。

推论：**习惯一致性必须按标题聚合，不能按 ID**——这与日历相反（日历必须按 ID）。两个系统用的是两套身份规则，不要混用。

### 会变的字段

- `dueDateLocal`：每日习惯完成后滚动到下一次（实测 41/192 个常驻 ID 变过）
- `title`：会改（实测 10/192）
- `isCompleted` / `completionDateLocal`：完成后写入，可能被改回（勾错再取消）

## 四、过去时间块是确定性事实（最容易被过度怀疑的一条）

**在一份快照内部，已经过去的时间块就是当时的行为记录，可以直接用陈述句讲。**

实测样例：今天（10-26 17:00）的快照里，`id 2165` 是

```
2026-10-25 13:00 → 16:30   修改简历，定稿汇联工作经历   lastModified 10-25 16:00
```

- ✅ 正确：「昨天 13:00-16:30 你在定稿汇联工作经历。」
- ❌ 错误：「昨天 13:00-16:30 可能在做定稿汇联（但记录可能被改过，不确定）。」

`lastModified 10-25 16:00` 落在活动区间内，说明这条记录是在进行中/刚结束时被调过时间的——这恰恰是**日志语义**的证据（用户按实际用时修正），不是可疑信号。给过去块加不确定性对冲，是把「跨快照会变」错用到「单份快照内」，既没有信息量，又让整份分析显得不可信。

**唯一需要留白的是「做完没有」。** 日历块只回答「当时在做什么」，不回答「这件事结束了没有」。完成判定的唯一依据是提醒事项的 `isCompleted`：

| 日历（过去块） | 提醒事项 | 结论 |
|---|---|---|
| 有 | 已勾选 | 做完了 ✅ |
| 有 | 未勾选 | **问用户「做完了没」**——做完了去勾选 / 没做完改截止时间 |
| 无 | 已勾选 | 数据缺口：补建追溯事件，或纠错勾选 |

## 五、跨快照会变 ≠ 单份快照不可信

两个层次必须分开，混在一起就会写出「昨天可能做了 X」这种既没用又伤信任的话：

- **层 1｜单份快照内**：过去块 = 事实。用陈述句，不加对冲。
- **层 2｜跨快照之间**：记录会被改写。想看「当时是怎么记录的」，用**当时那份快照**；最新快照只反映最终状态。事件被改到别的日期后，原日期在新快照里不再有记录——这不是「当时没做」，是记录被搬走了。

引用历史时按层 1 说事实；做跨期对比时按层 2 注明基于哪一份快照（`scan_time_local`）。

## 六、分析时必须遵守的五条推论

1. **取最新版本，不累加。** 同一 ID 在 23 份快照里出现 23 次，是**一件事**，不是 23 件事。任何「事件数」「总时长」统计必须先按 ID 去重，只保留最新版本。
2. **日历按 ID 对齐，提醒事项按标题聚合。** 两套身份规则，不可互换。
3. **按最终 `startDateLocal` 归属日期**，不按快照日期归属。跨天漂移的记录只算在它最后落的那一天，避免同一件事在两天各算一次。
4. **窗口外消失不是删除。** 判定删除需同时满足：最终 `startDateLocal` 仍在后一份快照 window 内 + 该 ID 未出现。
5. **变更本身是信息，不只是噪声。** 一条记录被改 9 次 = 这件事反复改期，本身就是执行状态信号（计划不稳定 / 回避）。分析「计划遵守度」时，`lastModifiedDateLocal` 的变动次数和跨度是直接证据，应当读出来，而不是把旧版本抹掉。

## 七、实测证据基线（2026-10-26）

| 项 | 数值 |
|---|---|
| 日历快照份数 | 23（10-21 → 10-26） |
| 日历 ID 总数 | 123 |
| 时间/时长改过的 ID | 57（46%），最多 9 个版本 |
| 标题改过的 ID | 21（17%） |
| 窗口内真删除 | **0** |
| 循环事件（`hasRecurrences=true`） | **0**（符合「不建循环」规则） |
| 提醒事项快照份数 | 27 |
| 提醒事项 ID 总数 | 381，消失 **0** |
| 同标题多 ID | 49 个标题（每日习惯实例） |

这些数字是判断「异常」的基线。例如某天突然出现大量 ID 消失，那是采集故障，不是用户行为。

## 八、读几份快照：判定表

**默认只读最新一份。**多读有成本（token、时间、误读风险），必须有理由才升级。三个判据，命中任一即升级：

1. **问的是「变化」而不是「状态」** → 需要序列
2. **问的是「当时的意图」而不是「当时的事实」** → 需要当时那份快照（最新快照里的旧记录已被改写）
3. **时间范围超出最新快照的 window（`daysBack 7` / `daysAhead 30`）** → 需要历史快照

### 三档读取

| 档位 | 读几份 | 适用 |
|---|---|---|
| **L0 单份**（默认） | 最新一份 | 状态诊断 |
| **L1 双份** | 首末 / 相邻 / 指定日 | 变化检测、意图还原 |
| **L2 序列** | 区间内全部 | 演化分析、故障排查 |

### 场景对照表

| 分析任务 | 档位 | 读哪几份 | 理由 |
|---|---|---|---|
| 今日态势、逾期、黑洞、今日行动指令 | L0 | 最新 | 状态问题，最新即当前 |
| 过去 7 天**单条事实**（「昨天 13:00 在做什么」） | L0 | 最新 | window 含过去 7 天，过去块 = 最终事实 |
| 习惯一致性趋势（7 天） | L0 | 最新 | 已完成实例保留在 `items` 内，按 `completionDateLocal` 回溯 |
| 过去 7 天**整天时间账**（总时长、完整事件集） | L1 | 那天**最后一份** | 最新快照的过去块是「最终修订版」：被改到今天的事件已不在昨天，总时长会偏小 |
| 今天计划 vs 实际 | L1 | 当天最早 + 当天最新 | 计划只存在于当时快照 |
| 「昨天原计划做什么」 | L1 | **昨天最早一份**（不是最新） | 最新快照里昨天的记录已被改写，读不出当时的意图 |
| 某任务改了几次 / 计划遵守度 | L2 | 该 `id` 出现过的全部 | 版本序列 = 改期证据 |
| 跨周对比、上周趋势 | L1 | 上周代表快照 + 最新 | 上周已滑出 7 天窗口 |
| 超 7 天历史（>7 天前做了什么） | L1 | 那天最后一两份 | 已滑出窗口，最新快照里没有 |
| 采集连续性 / 数据故障排查 | L2 | 区间内全部 | 缺份即故障 |

### 操作细则

- **「最新一份」按 mtime 排序取最后**，不要按文件名精确匹配时点——实测早间快照时点漂移在 `0823`~`0926` 之间，按 `0800` 匹配会落空。
- **「当天最早」** = 当天日期目录下按时间排序第一份；**「当天最后」** = 最后一份。实测每日 4 份（早间 / 13:00 / 17:00 / 22:00），当天 22:00 未到时只有 3 份。
- **读多份时必须按身份去重**（日历按 `id`、提醒按 `title`），只保留每条的最终版本，否则同一件事会被重复计入（见第六节推论 1）。
- **升级读取要说明理由**：在报告或会话里写一句「为判断改期次数，读取了该 ID 的 N 份快照」，让读者知道数据范围。
