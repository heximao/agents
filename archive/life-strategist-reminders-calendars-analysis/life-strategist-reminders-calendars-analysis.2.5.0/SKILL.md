# 提醒事项 + 日历执行分析

分析 Apple 提醒事项 + 日历快照数据的标准流程，用于诊断用户执行状态、检测回避模式入侵、下达按优先级排序的行动指令。整体运营模式见 `life-strategy-operations`，remindctl CLI 见 `apple-reminders`，字段规格见 `SPEC/REMINDERS.md` 和 `SPEC/CALENDARS.md`。

## 适用场景

- 用户要求分析提醒事项/日历数据来"推动目标达成"
- 每周/每月复盘或周期性自诊断
- 周六决策报告需要提醒事项+日历数据输入
- 用户问"我的执行情况怎么样"或类似状态问题
- 任何策略师在下达优先级之前需要态势感知的会话

## 前置条件

本 skill **只**从 `~/life/reminders/` 和 `~/life/calendars/` 读取数据。不读任何外部文件（task_state.json、changelog.md、日报）——那些属于 `life-strategy-operations`。

1. **提醒事项快照**：`~/life/reminders/archive/YYYY/YYYY-MM/YYYY-MM-DD/YYYY-MM-DD_HHMM_reminders.json`
2. **日历快照**：`~/life/calendars/archive/YYYY/YYYY-MM/YYYY-MM-DD/YYYY-MM-DD_HHMM_calendars.json`
3. **每周分析报告**（可选）：`~/life/reminders/analysis/weekly/YYYY/YYYY-MM/*_weekly_report.md`（注意前缀是日期时间，如 `2026-10-19-1046_weekly_report.md`，不是 `weekly_report_*`）

**所有数据仅来自归档——不做实时应用查询。**不得调用 `remindctl` 或读取 `Calendar.sqlitedb`。4 时点 cron（8/13/17/22）确保数据延迟永不超过约 5 小时。

## 数据采集顺序

在一个工具调用轮次内**批量执行独立读取**：

1. `date` — 当前时间
2. 检索最新提醒事项快照：`ls -t ~/life/reminders/archive/YYYY/YYYY-MM/*/*.json | head -5`
3. 检索最新日历快照：`ls -t ~/life/calendars/archive/YYYY/YYYY-MM/*/*.json | head -5`

第二轮（使用步骤 2-3 得到的路径）：

4. 解析最新提醒事项快照 JSON → 见 `references/parsing-logic.md`
5. 解析最新日历快照 JSON → 见 `references/parsing-logic.md`
6. `read_file` 最新每周分析报告：`ls -t ~/life/reminders/analysis/weekly/YYYY/YYYY-MM/*_weekly_report.md | head -1`

## 日历时间语义

四条原则决定日历时长必须如何解读。**解析日历数据前先加载 `references/calendar-time-semantics.md`。**

1. **30 分钟量化** — 粒度 30 分钟，最小 30 分钟，时长 = ceil(need/30)×30
2. **计划/日志二象性** — 过去事件 = 实际时间日志；未来事件 = 计划分配；边界 = 当前时刻
3. **并发事件合法** — 重叠不自动等于错误；仅当两者都需要同时主动投入时才标记
4. **短时日常任务不进日历** — 喂猫/泡茶/签到 放在提醒事项里；不进日历是正确的

## 核心目的

**本 skill 的存在意义是帮用户把时间花在重要的事情上——不是维持一份整洁的日程表。**

目标循环：**设定目标 → 推进目标 → 完成目标 → 设定新目标 → 循环**。每次分析必须先回答这个问题："用户的时间是否花在推进目标的工作上？"

其余一切——习惯打卡一致性、日程整洁度、时间卫生、系统健康——都是**次级基础设施**。它们的存在是服务目标推进，而不是取代目标推进。一套维护完美却零目标推进工作的习惯系统是危险信号，不是成功：

- 24/24 个习惯完成但没做职业/收入工作 → 系统运转完美却毫无用处
- 0 逾期、0 黑洞、日历排得满满当当 → 若没有时间流向目标，就只是整洁而空洞
- 系统任务占满黄金时段 → 基础设施维护伪装成生产力

**运行任何透镜（Lens）之前，始终先检查目标循环：**

1. 提醒事项的 career/项目列表中有没有带截止时间的**当前目标**？
2. 日历上是否已为它**分配时间**（透镜 7 正向检查）？
3. 目标是否正在**推进**——已完成的条目显示出进展（透镜 7 反向检查）？
4. 当前目标完成**之后**做什么——下一个里程碑是否已定义并排入时间块？

若其中任何一项缺失，那就是第一号发现——排在任何系统健康或时间卫生问题之前。日程整洁度与习惯打卡一致性作为次级状态汇报，绝不作为头条。

**分析报告是决策产物，不是观察报告。**用户在数据采集上投入巨大（4 时点 cron、归档规范化、扫描脚本）——这笔投资的回报是决策质量，不是更多分析。策略师做决策（做什么、按什么顺序、什么时间之前），用户执行。只呈现发现而不做决策的报告是不完整的。

## 分析框架

八个诊断透镜，按顺序应用。**加载 `references/analysis-lenses.md` 获取完整细节与交叉引用表。**

1. **系统健康** — 逾期/黑洞/习惯趋势基线
2. **系统任务入侵** — 对日历的工具过度投资闸门；过去 = 已确认的回避，未来 = 可取消的风险；收入主线任务循环 3 次以上且零外部验证（投递/开聊/反馈）= 完美主义式回避
3. **时间空档检测** — 未来时段 >2 小时无收入主线/专注工作 = 悬崖；过去的空档 = 未记录（不是问题）
4. **收入路径覆盖** — career 列表 ↔ 日历时间块；简历之后有没有投递/面试的时间？
5. **时间卫生** — 睡眠 >01:00、早餐 >11:00 = 偏晚；连续 3 天以上 = 标记
6. **黑洞扫描** — 元规则（保留）、真黑洞（标记）、系统标记（若与职业工作争夺注意力则标记）
7. **提醒事项 ↔ 日历一致性** — 正向：重要任务没有日历时间块；反向：已完成任务没有日历记录（补建/纠错）
8. **过去/未来事件语义** — 过去时间块 = 行为日志（花了时间做 X ≠ 任务完成）；未来时间块 = 计划（可变）；过去时间块 + 提醒事项未勾选 → 问用户做没做完，绝不把同一事项同时放进 今日完成 和 今日到期未完成

## 输出结构

```
# 📊 提醒事项 + 日历日程分析 | YYYY-MM-DD 周X HH:MM

## 结论先行
<1-2 句评估：用户的时间是否花在推进目标的工作上？先陈述目标循环状态（已设定/推进中/已完成/下一步已定义），再谈任何系统健康观察。>

## 一、数据全景
### 提醒事项（快照时间）
<表格：关键指标，附 ✅/⚠️/🔴>
### 日历（今日事件）
<表格：时间 | 事件 | 日历 | 性质(✅/⚠️/❌)>
### Career 列表冲刺进度
<表格：状态 | 模块 | 截止时间>

## 二、问题诊断
### 🔴 P1: <最关键>
### 🔴/🟡 P2: <次关键>
### 🟡 P3+: <更低优先级>

## 三、行动指令
### 今天（日期，当前时间）
### 本周
### 系统清理（不占工作时段）

## 下一步动作
<一条具体的下一步动作，带时间约束>
```

### 优先级分类

- **🔴 P1**：本周正在实际阻碍目标达成
- **🟡 P2**：不处理就会演变成阻碍的结构性风险
- **🟢 P3**：背景性改进

### 时间纪律检查（在下达任何"今天做这个"的指令之前）

1. 实际截止时间是什么？（来自提醒事项快照 `dueDateLocal`）
2. 现在几点？（来自 `date`）
3. 用户今天已经做了什么？（来自快照 `completionDateLocal`）
4. 紧迫性是真实的（≤24 小时且未完成）还是人为制造的（还差好几天）？

推送新事项之前，先确认已完成的工作。

## 常见陷阱

**执行前先加载 `references/pitfalls.md`** — 17 条陷阱，覆盖：priority 字段类型崩溃、camelCase 日历字段、30 分钟网格异常与时长量化、重叠时长高估、UTC/北京时间、dueDate 过时、已完成习惯的 recurrenceRule 剥离、空分组键省略、快照时点语义、元规则不是黑洞、13:00 触发器退役（由 cron 54cff38091c1 替代）、系统任务 = 回避证据、系统清理不作优先项、已完成任务无日历事件的一致性缺口、进行中事件 endDate 与活动链完成时间混淆、日历过去/未来事件语义（行为日志 vs 计划，完成 ≠ 时间块）、用户引语时间归因（引用反馈时使用实际记录日期或不带时间指向——绝不臆造相对周期）。

## Skill Self-Update（自我更新）

当用户报告分析报告中的严重错误或遗漏时，响应必须是两层的——绝不能只修实例：

1. **立即修复**：在当前会话中纠正报告里的具体发现；明确承认错误。
2. **系统级根因**：追问 skill 流程的哪一层放过了这个错误——是缺失一条原则、缺失一条陷阱、缺失一个透镜、缺失一项交叉引用检查，还是已有规则未被遵守。被报告的错误是症状；流程缺口才是原因。
3. **修补 skill**：更新相关部分（原则 / 陷阱 / 透镜 / reference 文件），让整类错误都被预防，而不只是这一个实例。提升 skill 版本号。**下方记录的每条示例必须携带实际日期 — `← user (YYYY-MM-DD HH:MM): …` —** 后续分析运行会引用这些示例，而不带日期的引语会诱使某次运行为可能只有几小时历史的反馈臆造时间周期（"上周"）。旧的无日期示例为 日期未知：引用它们时不带任何时间指向，绝不使用相对周期。
4. **复发升级**：若修补后同类错误再次出现，说明修补的抽象层级不对——把修复往上抬一级（例如原则 3 修补后重叠仍被误判，说明分类标准太模糊，而不是需要再补一个示例）。
