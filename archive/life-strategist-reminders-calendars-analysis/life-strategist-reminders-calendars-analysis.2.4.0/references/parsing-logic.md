# Pitfalls

17 pitfalls discovered during real analysis execution. Load this before running the analysis.

- **`priority` field is int OR string — `>=` comparison crashes mid-parse.** Always coerce with `int(x.get('priority', 0))` wrapped in try/except. A crash at line 52 of a 70-line parsing script loses the entire output.
- **Snapshot field names must match source exactly — wrong lookups silently return None (no KeyError).** Calendar fields are camelCase: use `startDate`, `startDateLocal`, `endDateLocal`, `allDay`, `hasRecurrences`, `recurrenceRule`, never `start_date`. Reminders list-name field is `list` — filtering project lists with `listName` matches zero items. See `scripts/scan-calendars/README.md` for the full field table.
- **Event durations off the 30-min grid are anomalies, and time-sums are quantized.** Calendar rule: 30-min granularity, 30-min minimum, +30-min steps beyond (durations = ceil(need/30)×30). A 45-min event violates the grid — flag it. And because short tasks inflate to the 30-min floor, calendar totals overstate actual effort on short tasks; use durations for allocation/rhythm analysis, not stopwatch-precision accounting.
- **Summing overlapping event durations overstates wall-clock time.** Concurrent events (Principle 3) mean the same wall-clock minute can be logged under two or more events. For time-accounting totals, de-duplicate by wall-clock time (union of intervals), not by summing raw durations — otherwise 1 hour of actual time with two overlapping events reads as 2 hours.
- **`completionDate` in the snapshot is UTC; `completionDateLocal` is Beijing time.** `01:23` UTC = `09:23` Beijing. Use `completionDateLocal` for all date comparisons; never slice `completionDate` directly without converting first — the date boundary shifts by 8 hours.
- **Recurring reminders' `dueDate` is stale** — an incomplete daily habit keeps its original/past dueDate, not the next occurrence. Do not compute "due today" from dueDate arithmetic for habits; classify them by `recurrenceRule.frequency == 'daily'` and treat all incomplete daily habits as "due today". For non-habit items, the `dueDateLocal[:10] == today` check is safe because one-off/weekly/monthly items carry their real due date.
- **Completed daily-habit instances lose `recurrenceRule` (Apple strips it on completion).** A collection-layer `isHabit = (recurrenceRule.frequency == 'daily')` marks completed instances as `false`. For habit-consistency analysis, build the active-habit title set from incomplete daily-habit items, then match completed items by title against that set — this is an analysis-layer technique (the collection layer faithfully records the stripping; do not "fix" it in the collection script).
- **Snapshot `lists` count layer omits keys for empty groups** — a list with 0 items simply doesn't appear in the `lists` dict. Key-absence ≠ count-zero; state the evidence basis ("key missing vs prior snapshot") not "went to 0".
- **Snapshot reflects scan-time state, not real-time.** The 09:21 snapshot showing 0 completed-today doesn't mean 0 were done — it means 0 were recorded as complete at 09:21. The 13:00 snapshot will capture items completed between 09:21 and 13:00. Analyze the archive as-is; do not supplement with live `remindctl` calls — the archive is the canonical source and the 4-slot cron ensures data is never more than ~5 hours stale.
- **Meta-rules in 收集箱 are not black holes.** Items titled 【Agent请跳过】 are the user's manual task-classification rules (①立即做→闹钟 ②固定时间→日历 ③<15min→提醒). They are intentionally kept incomplete with no due date. Never flag them for deletion; skip them in the black-hole scan.
- **13:00 饭后触发器已退役（2026-10-21），午后启动由 cron job 54cff38091c1 驱动。** 原 Apple Reminder 13:00 每日重复项已被「每日-提醒事项-日历-跟踪」cron 替代——该 cron 在 8/13/17/22 时点 10 分运行，加载 life-strategist-reminders-calendars-analysis skill 分析快照并推送微信消息，内容覆盖原触发器催行动功能 + 上午时间诊断 + 日历时间块 + 下一步动作。不再需要在 Reminders 快照中检查 13:00 触发器项；分析运行本身即证明午后启动机制在工作。
- **System tasks on the calendar are avoidance-pattern evidence, not innocent scheduling.** When you see "更新性格" "Cron功能开发" "profile.yaml" "SOUL更新" "gitignore" in prime work hours, apply the Tool Over-Investment Gate: does this produce income within 2 weeks? No → flag as system-task invasion. The user's core avoidance mechanism is substituting system building for income action; the calendar is where this shows up objectively.
- **Do not recommend system-cleanup as a priority action item.** "Clean up your reminders list" or "reorganize your calendar" is itself a system-management task that triggers the same avoidance loop. If the analysis surfaces cleanup needs, batch them into a "系统清理（不占工作时段）" section explicitly labeled as weekend/evening work, never as a top priority.
- **A completed Reminders task without a calendar event is a data integrity gap, not just a missing record.** Per Principle 2, past calendar events are the user's actual time log. A completed non-habit task with no corresponding past event means either the event wasn't created (补建 needed) or the completion was wrong (纠错 needed). The backward check (Lens 7) catches this — but title matching is fuzzy: use keyword overlap (e.g., "简历" in both the reminder title and the calendar event title), not exact match, since the user may phrase them differently across the two systems.
- **进行中事件的 endDate ≠ 整个活动链的完成时间。** 13:15 分析时"做午餐"(12:30-13:30) 正在进行，endDate=13:30 是"做完午饭"，分析却表述为"13:30吃完"——实际后续紧接"吃午餐"(13:30-14:00)，14:00 才吃完。双错：①只取当前事件 endDate 作为"完成时间"，未追踪后续同主题事件链（做→吃是连续活动）②自然语言混淆"做完"与"吃完"。规则：分析"用户何时完成 X 活动"时，沿后续同主题事件链追踪到末事件 endDate 作为真正完成时间；表述严格区分 startDate="开始"、endDate="结束"，不得将 startDate 或前序事件 endDate 说成整个活动链的“完成”时间。
— 分析处理日历 JSON 时必须始终区分过去/未来事件语义（Principle 2）。过的时间块 = 用户实际做了什么（行为日志），不代表任务完成——“16:00-17:00 做了 social 简历” ≠ “social 简历写完了”，是否完成要看 Reminders isCompleted。未来的时间块 = 用户计划做什么（计划分配），不代表确定事实——用户随时会改 title/时间/删除。规则：①过去时间块用“花了X时间做Y”而非“完成了Y”②未来时间块用“计划X做Y”而非“已排好Y”③任务完成状态以 Reminders isCompleted 为准，不以日历时间块存在为准④用户反馈“已完成/已删除/已改时间”时，以用户反馈为准。⑤日历有过去时间块 + Reminders 未勾选 = 状态不一致 → 报告结论问用户“做完了没？”→ 完成了→提醒去 Reminders 勾选完成 / 没完成→提醒修改 Reminders 截止时间。不得同时放在“今日完成”和“今日到期未完成”两个矛盾位置。
- **引用用户反馈/历史事件时禁止发明时间周期。** 报告中引用用户说过的话，时间表述只允许两种：①实际记录日期（“你 10-23 说过…”）②无时间指向（“你自己说过…”）。除非该周期可在快照数据（dueDateLocal / completionDateLocal / 文件名日期 / 示例日期标注）中验证，否则不得使用“上周 / 前几天 / 之前 / 那天”等相对周期。技能 Self-Update 示例是历史反馈的主要文本来源，旧示例可能不带日期——无日期 = 日期未知，引用时不赋予任何时间。实测案例（2026-10-23）：17:10 报告把当天 12:09 的用户反馈写成“你上周自己说过‘为了写简历而写简历让我抗拒’”——反馈实际只有 5 小时历史，“上周”纯属臆造，用户当场识破（“时间周期错位”）。教练引用错误的时间记忆比不引用更伤信任：它让整个分析系统的时序可靠性存疑。
