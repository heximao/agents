# 分析框架与交叉引用检查

八个诊断透镜按顺序应用，外加五项双向交叉引用检查。**解析完两份快照后加载本文件。**

## 分析框架

数据采集并解析完成后，按顺序运行这**八个诊断透镜**。每个透镜产出一条发现，喂给行动指令。

### 透镜 1：系统健康（定量基线）

- 逾期数：0 = 健康 ✅；>0 = 回避信号（逾期持续累积 = 回避模式的客观数据）
- 黑洞数：真黑洞（无 dueDate、无重复、非元规则）应为 0
- 习惯一致性趋势：上升 = 恢复；持平/下降 = 中断
- 完成率：已完成/总数——仅作背景参考（每日习惯完成会机械地推高它）
- 重复标题：完全同标题、同截止日、不同 ID 的条目会虚增今日到期数——按唯一标题统计到期条目，并把完全重复项标记待删

### 透镜 2：系统任务入侵（日历上的工具过度投资闸门）

用户的首要回避机制是用系统/工具工作替代能产生收入的行动。把这个闸门直接套在日历事件上：

对今天日历上的每个事件问一句：**这件事能在 2 周内产生收入或推进求职吗？**

- ✅ 收入主线：写简历、收集 JD、方向探索、面试准备、投递
- ⚠️ 系统任务（回避风险）：Hermes 配置、profile.yaml、SOUL 更新、cron 开发、性格更新、脚本优化、AGENTS.md 编辑、gitignore 清理
- ❌ 两者都不是：吃饭、睡觉、休息（中性，不是回避）

**任何占据黄金工作时段（09:00-12:00、14:00-18:00）的 ⚠️ 事件都要标记。** 系统任务放在晚间/周末槽位没问题；放在黄金时段就是伪装成生产力的回避。

**重叠检测**：重叠事件**不自动**等于错误（原则 3——agent 代理的并发工作合法）。只有当两个事件都需要用户同时主动投入注意力时才标记为冲突（例如两个会议，或边写代码边通话）。如果一个事件是后台/agent 代理、另一个是主动专注工作，重叠是合法的并行工作——不要标记为错误。

**过去 vs 未来的权重**：⚠️ 事件在过去槽位 = 已确认的回避行为（黄金时段确实被消耗——最强证据）；⚠️ 事件在未来槽位 = 尚可取消的计划风险——建议在它消耗黄金时段之前挪到晚间/周末。

**孤立循环检查（收入主线完美主义）**：一个通过 2 周闸门的收入主线任务，仍然可能是回避——同一个产物在没有外部验证的情况下反复循环重写（例如「修改简历」在 career 列表里逐日再生成）3 次以上，而投递/申请/真人反馈始终为零，就是完美主义式回避。闸门必须检查反馈闭环，而不只是任务类别：当 career 列表反复重写同一份产物、而投递/开聊计数为零时，发现应该是缺失的外部里程碑（定义带截止时间的投递/开聊），绝不是再给更多编辑时间块。

### 透镜 3：时间空档检测

扫描**未来槽位**（此刻 → 当天结束），找出工作时段（09:00-22:00）内**超过 2 小时**、且用户没有排入收入主线或专注工作的空档。这些是会让一天停滞的生产力悬崖。注意：空档里可能合法地包含短时日常任务（喂猫、泡茶），它们本来就不该上日历（原则 4）——只有既无日历事件、又无日常任务填充的空档，才是真悬崖。过去的空档语义不同——未记录时间（休息、吃饭、未跟踪活动），不自动等于流失时间；不要把过去的空档标为悬崖。

最关键的缺口模式：**12:00-15:00（午饭后）**。**13:00 Apple Reminder 已退役（2026-10-21），午后启动由 cron job 54cff38091c1「每日-提醒事项-日历-跟踪」驱动**——该 cron 在 8/13/17/22 时点 10 分自动推送分析消息（含催行动 + 时间块 + 下一步动作），功能覆盖并升级了原触发器。不再需要在 Reminders 快照中检查 13:00 触发器项；分析运行本身即证明午后启动机制在工作。Post-lunch gap（12:00-15:00 无 focus work）仍需检查，但触发器缺失不再是 P1——触发器已迁移到 cron 层。

### 透镜 4：收入路径覆盖

把提醒事项里的 career 列表与日历事件交叉比对：

- 简历各模块有没有排进日历？（每个 career 列表条目都应有对应的日历时间块）
- 简历完成之后的下一个里程碑有没有时间？（投递/面试/JD 回应）
- 方向探索（BOSS JD 搜索、自由职业搜索）有没有日历时间块？

如果所有 career 日历块都只是「写」，没有「投/回应」，收入路径就有天花板——标记出来。

### 透镜 5：时间卫生

- 睡眠事件开始时间：>01:00 = 睡得晚（压缩早晨窗口）
- 早餐时间：>11:00 = 太晚（推迟有效启动）
- 这些是趋势信号，不是单日警报——但连续 3 天以上偏晚值得标记

### 透镜 6：黑洞与陈旧条目扫描

在 `no_due` 桶里区分：

- **元规则**（标题以【Agent请跳过】开头）——用户的任务分类参考，保留，不标记
- **真黑洞**（开放式标题如「寻找机会XXX」，无截止、无重复）——标记为降级为限时复审或删除
- **系统标记**（hermes 列表里的【Issues】【Plan】【Task】）——看板/系统标记，不是真任务；若它们与 career 工作争夺注意力则标记

### 透镜 7：提醒事项 ↔ 日历完整性（双向校验）

两个系统必须互相校验。提醒事项里有、日历里没有时间块的任务，有永远做不完的风险；已完成任务没有日历时间记录，是数据完整性缺口。

**正向检查（提醒事项 → 日历）：>15 分钟任务必须有时间分配。**

依据用户规则「超过 15 分钟的提醒事项，必须有日历日程分配」（见 `user-maintenance-rules.md` 第三节）——这条是**无条件**的，不限于项目列表。但按影响分两档输出，避免报告被低价值提示淹没。

筛选范围：未完成、非每日习惯、预估耗时 >15 分钟的条目。耗时判定顺序：

1. 标题或备注里有明确时长（「30 分钟」「1 小时」）→ 直接用
2. 同标题历史日历块的实际时长 → 作为估值
3. 两者都无 → 按类别推定：喂猫、泡茶、签到、洗漱、刮胡子、洗衣晾晒等短时日常任务视为 ≤15 分钟（跳过）；其余视为 >15 分钟

**匹配必须一对多**：用户规则允许「同一个提醒事项拆分为多个日历日程完成」。把所有标题关键词重叠、日期在截止日当天或之前的未来事件时长**加总**，与预估耗时比较——完全无事件 = 缺块；有事件但加总时长明显不足 = 分配不足，同样标记。只找到一块就判定「已分配」是错的。

**标题匹配前先剥离 emoji**（采集层无法识别表情，不剥离会导致两侧标题永远匹配不上）。

分档：

- **P1 档**：career/项目列表条目、或优先级 ≥5、或截止 ≤3 天 → 缺块直接进 P1，指令是「现在就排一个块」
- **P3 档**：其余 >15 分钟条目 → 只作「时间未分配」提示，合并成一行列出，不占优先级

**反向检查（日历 → 提醒事项）：已完成任务没有时间记录。**

对每条已完成、`completionDateLocal` 落在最近 7 天内、且**不是**每日习惯的提醒事项（习惯是短时日常任务，按原则 4 不进日历）：

检查完成日期当天或附近是否存在对应的**过去**日历事件（标题关键词重叠，同样先剥离 emoji）。若无 → 标记：「任务 `{title}` 在 `{date}` 标记完成，但不存在日历时间记录——要么补建一个追溯事件记录实际用时，要么在完成标记有误时纠错。」

### 透镜 8：过去/未来事件语义检查

检查分析输出是否正确区分过去/未来事件（原则 2）：

1. **过去的时间块**（endDateLocal < now）= 用户实际做了什么（行为日志）。分析输出时用「花了 X 时间做 Y」而非「完成了 Y」。是否完成以 Reminders isCompleted 为准——日历时间块存在 ≠ 任务完成。
2. **未来的时间块**（startDateLocal > now）= 用户计划做什么（计划分配）。分析输出时用「计划 X 做 Y」而非「已排好 Y」。用户随时会改 title/时间/删除——不要当作确定事实。
3. **跨边界事件**（start < now < end）= 正在做的事。分析输出时用「正在做 Y」。
4. **交叉校验：日历过去时间块 + Reminders 未完成** — 当日历有过去的时间块（endDateLocal < now）且对应 Reminders 任务未勾选（isCompleted = false）时，这是状态不一致。报告结论：问用户「做完了没？」→ 完成了→提醒去 Reminders 勾选完成 / 没完成→提醒修改截止时间。不得同时放在「今日完成」和「今日到期未完成」两个矛盾位置。

错误模式（必须避免）：

- ❌ 「今日完成 ✅：social 项目（16:00-17:00）」 — 把过去时间块等同于任务完成
- ❌ 同时放在「今日完成」和「今日到期未完成」 — 自相矛盾
- ✅ 「social 做完了没？完成了去 Reminders 勾选；没做完改截止时间」 — 交叉校验行动指令
- ❌ 「日历已经排好了：14:00-15:30 social」 — 把未来计划当作确定事实
- ✅ 「计划 14:00-15:30 做 social（可能调整）」

## 交叉引用检查

分析的力量来自交叉引用多个数据源，而不是任何单一数据源：

| 检查 | 数据源 A | 数据源 B | 看什么 |
|------|---------|---------|--------|
| 重要任务 ↔ 日历时间块（正向） | 未完成、非习惯、耗时 >15 分钟的提醒事项（分 P1/P3 两档，见透镜 7） | 日历未来事件（一对多匹配、时长加总） | 每个 >15 分钟任务都应有足量未来时间块；缺块或分配不足 → P1/P3 分级标记（透镜 7 正向） |
| 已完成任务 ↔ 日历历史（反向） | completionDateLocal ≤7d 的已完成非习惯提醒事项 | 日历过去事件 | 每条已完成的非习惯任务都应有过去日历事件；若无 → 标记补建或纠错（透镜 7 反向） |
| Career 冲刺 ↔ 日历时间块 | 提醒事项 `career` 列表未完成条目 | 日历 `工作` 事件 | 每条 career 列表任务都应映射到日历块；未排程的 career 任务是风险 |
| 习惯一致性 ↔ 周报 | 快照的 7 天习惯趋势 | 最新 `*_weekly_report.md`（`reminders/analysis/weekly/YYYY/YYYY-MM/` 下） | 趋势相对周报评估是在加速、稳定还是退化 |
| cron 54cff38091c1 状态 | cron 输出目录 `~/.hermes/profiles/life-strategist/cron/output/54cff38091c1/` | 当日是否有分析输出文件 | 13:00 触发器已退役迁移至 cron；若当日无 cron 输出文件 = 午后启动机制失效，flag P1 |
